# MAGMA Threads v1.2 게시 안전장치 설계

## 목적

활성 워크플로의 후보 선택 승인과 실제 게시 승인을 유지하면서, 초안 작성 단계에서 Threads 연결 상태와 중복 위험을 먼저 차단한다. 자격증명은 BlueKiwi에 저장하지 않으며, 실행 중인 Hermes 프로세스가 시작 시 Bitwarden Secrets Manager에서 주입한 값만 사용한다. 토큰·사용자 ID·계정 식별값은 어떤 화면, 단계 출력, 아티팩트, 로그에도 기록하지 않는다.

## 현재 상태와 버전 전략

- 대상: `MAGMA Threads 콘텐츠 발행` v1.1 (workflow ID 6)
- 새 버전: v1.2. 기존 v1.1의 실행 태스크 #1은 정본 판단 Gate에서 보류한다.
- 사유: 새 버전은 기존 실행의 단계 스냅샷을 바꾸지 않으며, 보류 중인 태스크는 아직 외부 게시 호출을 하지 않았다.

## 비교한 접근

1. 권장 — v1.2에서 기존 초안·중복 점검 단계를 확장한다. 후보 선택 승인과 최종 게시 승인의 위치를 유지하면서, 한 단계에 연결 검사·90일 이력·로컬 기록 중복 검사를 강제한다. 변경 범위가 작고 승인 분리가 유지된다.
2. 새 preflight 단계를 후보 승인 뒤에 삽입한다. 검사 경계는 명확하지만 초안 작성과 검사 결과가 분리되어 단계 수와 상태 전달이 늘어난다.
3. BlueKiwi 자격증명으로 Threads를 연결한다. 이 방식은 자격증명 저장 금지 요구와 충돌하므로 제외한다.

## v1.2 변경 설계

### 단계 6 — `선택 후보 초안·연결·중복 사전점검`으로 교체

1. 후보 선택 Gate의 승인 결과를 확인한다. 보류 또는 수정 요청이면 초안·외부 조회·게시 준비를 중단한다.
2. 실행 중인 Hermes 환경에서 Bitwarden 공급자가 이미 주입한 Threads 토큰과 사용자 ID만 참조한다. BlueKiwi credential을 생성·연결·저장하지 않는다. 값 자체와 값으로부터 복원 가능한 식별자는 출력, 파일, 로그, `context_snapshot`에 쓰지 않는다.
3. `/me` 읽기 전용 요청을 정확히 한 번 수행한다. 성공 여부, HTTP 상태 범주, 계정 일치 여부만 기록하며 사용자 ID·토큰·사용자명·원문 응답은 기록하지 않는다. 연결 검사 실패나 불명확 응답이면 `connection-blocked` 상태로 차단한다.
4. 연결 검사 통과 후 Threads의 최근 90일 게시 이력을 읽기 전용으로 조회한다. 후보의 정규화 텍스트와 SHA-256 중복 키, 제목·핵심 주장 유사도를 비교한다. 로컬 `content/posts/` 및 `~/.hermes/company/threads-publishing/publish-log.md`도 같은 키와 유사도로 비교한다.
5. Threads 원격 이력 또는 로컬 기록에서 정확 중복·임계치 이상 유사·조회 불확실성이 발견되면 `duplicate-blocked` 또는 `history-unconfirmed`으로 차단하고 최종 승인 Gate를 열지 않는다.
6. 모든 검사를 통과한 후보만 Threads 본문과 프로젝트 발행용 초안을 만든다. 본문과 payload에는 근거·경로·승인 메모·자격증명·계정 식별값을 포함하지 않는다.

### 단계 7 — 실제 게시 승인 유지·강화

최종 승인 화면은 기존 승인/수정/보류 선택을 유지한다. 단, `/me` 연결 상태, 원격 90일 이력 확인, 로컬 기록표 확인, 중복 키 판정, 비노출 검사는 `통과/차단` 상태와 사유 코드만 표시한다. 시크릿, 사용자 ID, 원문 API 응답, 헤더는 화면에 표시하지 않는다.

### 단계 8 — 게시·검증·기록 루프 강화

1. 최종 승인 직후 발행 가능한 상태를 다시 검증하고 immutable `attempt_id`와 payload 해시를 만든다. 이 둘은 내부 로그에만 기록한다.
2. 기존 통합에 단일 HTTP 게시 엔드포인트가 확인된 경우에만 물리적으로 한 번의 외부 POST를 전송한다. 단일 엔드포인트가 없으면 `manual-confirmation-required` 상태로 종료하며, Threads의 다단계 생성/발행 호출을 자동으로 대체·반복하지 않는다.
3. 네트워크 오류, 타임아웃, 2xx 이외 응답, 응답 본문 파싱 실패, 결과 URL·게시 ID 부재는 모두 `publish-uncertain`으로 남긴다. 자동 재게시·자동 재시도·같은 payload의 재전송을 수행하지 않는다.
4. 명확한 성공 응답만 `published`로 기록한다. 내부 로그에는 상태·시각·payload 해시·중복 키·안전 검사 결과·응답 요약만 남긴다. 토큰·사용자 ID·원문 응답은 `[REDACTED]` 처리한다.

## 실패 상태

| 상태 | 외부 게시 | 다음 조치 |
| --- | --- | --- |
| `connection-blocked` | 금지 | Hermes Bitwarden 주입·읽기 권한을 운영자가 확인 |
| `duplicate-blocked` | 금지 | 다른 후보 선택 또는 수정 |
| `history-unconfirmed` | 금지 | 원격 이력 조회를 수동 확인 |
| `manual-confirmation-required` | 금지 | 단일 HTTP 게시 통합을 마련하거나 수동 게시 |
| `publish-uncertain` | 자동 재게시 금지 | Threads 관리 화면 또는 운영자가 결과를 확인 |
| `published` | 완료 | 로그 기록 후 회차 종료 |

## 검증 기준

- BlueKiwi 자격증명 목록은 비어 있으며 새 자격증명을 만들지 않는다.
- `/me`는 GET 한 번만 수행하며 시크릿·식별값이 모든 산출물에서 누락된다.
- 원격 90일 이력과 로컬 `content/posts/`, `publish-log.md`가 모두 중복 검사의 입력으로 기록된다.
- 최종 승인 전에는 게시 HTTP 요청이 없다.
- 최종 승인 후에는 단일 HTTP 게시 통합이 있는 경우 한 번만 전송한다. 응답이 불명확하면 재전송 없이 `publish-uncertain`을 남긴다.
- 기존 후보 선택 승인과 실제 게시 승인은 각각 독립 Gate로 유지된다.
